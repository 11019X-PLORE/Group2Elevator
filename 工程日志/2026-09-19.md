# Elevator Demo Engineering Log — 2026-09-19

## English

### Daily Goals

- Rebuild ElevatorDemo on the control pattern ArmDemo validated: AdvantageKit IO layer, one-press movement commands, software travel limits, NetworkTables-tunable speed/acceleration ceilings, and AdvantageScope telemetry — reduced to the elevator alone.
- Collapse the calibration to a single fill-in limit: unlike ArmDemo's elevator (two per-motor travels of 3.4 / 14.5 rotations plus the arm interlock), this project measures one averaged travel, `Constants.Elevator.MAX_EXTENSION_ROTATIONS`, and refuses every movement until it is filled.
- Keep zero hardware dependencies on the arm: no interlock, no hold command, no through-bore switch — the elevator is standalone.

### Completed Work

- Ported the AdvantageKit IO pattern from ArmDemo: top-level `ElevatorIO` contract (`updateInputs` poll + `@AutoLog` inputs container + mirrored `setMotorVoltages`) and the real-hardware `ElevatorIOTalonFX` (Brake neutral mode, one `BaseStatusSignal.refreshAll` transaction per cycle, applied voltages reported back through the inputs). Added the `akit-autolog` annotation processor to `build.gradle`.
- Rewrote `ElevatorSubsystem` around one calibration value: `OptionalDouble maxExtensionRotations` (empty while the constant is 0 or mistyped). All limit logic runs in fractions of that travel, so the sign of the filled value carries the winding direction — a negative measurement still works, and every voltage sign follows it via `Math.signum`. Either motor reaching the shared upper/lower limit stops both motors; the mid command keeps ArmDemo's latched-direction pattern.
- Ported the safety ceilings unchanged: signed-voltage slew (direction reversals ramp through zero) and the normalized travel-fraction speed cap (faster motor wins), both NetworkTables-tunable (`/SmartDashboard/Elevator Max Travel (/s)`, `Elevator Voltage Slew (V/s)`), 0 disables, mistyped values fall back to defaults.
- Movement commands carry the uncalibrated guard in their finish conditions (`!isCalibrated() || atLimit()`), so an unfilled limit constant ends commands immediately at zero volts instead of driving the mechanism.
- `Robot` switched from `TimedRobot` to `LoggedRobot` with `NT4Publisher`; `RobotContainer` slimmed to wiring only: `ElevatorIOTalonFX` + the one limit from `Constants` + buttons 3/1/6 (same raw numbers as ArmDemo's elevator, `onTrue`). Deliberately no startup `zeroEncoders()` — TalonFX positions must survive a code restart (same safety reasoning as ArmDemo).
- 16 unit tests (`ElevatorSubsystemTest` + `FakeElevatorIO`): positive extension readout, the uncalibrated gate (direct calls and commands), zeroing, either-motor shared-limit trip, mirrored ±2V outputs, negative-calibration direction following, both command stop paths, slew/speed-cap statics, non-finite fallback, through-zero reversal, both mid-command directions, immediate finish past mid, and action timing records. Tests inject zero ceiling suppliers (limits off) so assertions do not depend on real elapsed time; the two ceiling-specific tests inject their own values.
- Two porting bugs caught by the tests and fixed: (1) the mid-extend test started with motor 2 already past half travel — the "either mechanism arrives first" rule correctly refused to move, so the test data moved below mid; (2) a dt of exactly zero between construction and the first movement makes the ramp correctly hold zero volts, so the reversal test now sleeps 2 ms before its first movement.
- Full build green, 16/16 tests passing.

### Why It Matters

- The deploy-then-measure-then-fill workflow is now one step: the elevator cannot move until the one limit is real, and it needs nothing else — CAN IDs and buttons are already correct in `Constants`.
- Sign-following calibration means the same code runs unmodified on either winding direction: whatever number AdvantageScope shows at the top is the number to fill.
- Keeping ArmDemo's IO pattern, telemetry keys, and ceiling behavior means log replay, AdvantageScope layouts, and tuning habits transfer directly.

### Next Steps

- On-robot: measure `MAX_EXTENSION_ROTATIONS` by hand-raising the elevator with the robot disabled, fill the constant, and verify buttons 3/1/6 against the real mechanism.
- Confirm the winding direction on the real rig matches the documented convention (raw decreases while extending); if not, fill the negative measured value — no code change needed.

## Second pass — audit and fixes / 第二轮：审查与修复

### English

The first pass shipped a calibration model that was wrong on the rig it was ported from. Reviewing
this project against `clone-projects/ArmDemo` turned up six problems, all now fixed:

1. **Lost travel.** ArmDemo measured this bench elevator at **3.4 rotations on motor 1 and 14.5 on
   motor 2** and normalizes each motor by its own travel. Collapsing that into one averaged value
   makes "whichever motor arrives first" trip at 8.95 of motor 2's 14.5 rotations, i.e. the elevator
   stops at **62% of its stroke** and the half-travel preset lands at **31%** — failing in the safe
   direction, which is why it looked fine. `ElevatorCalibration` restores per-motor travels as the
   coordinate, keeps one shared value for genuinely symmetric rigs, and the README's "read the
   average at the top" instruction — the exact step that produced the bad number — is gone.
2. **A limit check that could not see the current cycle.** Limits were evaluated in each command's
   `execute()`, and `CommandScheduler` runs `execute()` before the subsystem's `periodic()`, so every
   decision acted on a 20 ms-old snapshot and the last approved voltage stayed on the wires for a
   cycle past the stop. All output now comes from `periodic()` against a `MotionMode` the commands
   only request; `theSubsystemCutsTheOutputInTheSameCycleItSeesTheLimit` pins the behavior down.
3. **Frozen CAN read as "not at the limit".** `refreshAll`'s result was discarded. The IO now reports
   whether each drive has answered, whether its last transaction was clean (`isAllGood`), and how old
   the reading is; the subsystem treats any of those as untrusted and writes zero volts. The age
   budget is a live tunable and `0` disables that one test, so if this clock base behaves differently
   on a roboRIO an operator can isolate it from the dashboard. Positions are also latency-compensated
   against their velocity signal now.
4. **`zeroEncoders()` had no caller.** It is now `rezeroAtLowerLimit()`, accepted only while the
   mechanism rests on its lower stop, bound to button 7. Zeroing mid-travel would silently shift every
   software limit, so the physical premise is enforced in code.
5. **Sign ambiguity.** One signed travel constant was trying to encode both the encoder mounting and
   the wiring direction, and the code could not tell them apart — so "fill a negative measurement and
   every sign follows" was not reliably true. They are two explicit constants now, travels are positive
   magnitudes, and a mechanism that demonstrably moves against its command latches
   `Elevator/DirectionReversed` and stops.
6. **Hygiene.** `vendordeps/AmLib-2026-Latest.json` had zero imports and is gone; so is a stale local
   `bin/` tree. `.github/workflows/test.yml` runs the suite on push and PR, which it previously had
   no runner for.

Added to make it worth someone else's time: `ElevatorIOSim` (mock stage behind the same interface, so
`./gradlew simulateJava` exercises the real control loop on a laptop), proportional presets
(`moveToFractionCommand`, `holdAtFractionCommand`) with a gravity feedforward deliberately defaulting
to 0 V, a `CalibrationSuspect` diagnostic that catches the §1 mistake during the calibration
measurement itself, and **42 tests** on a manual clock — the `Thread.sleep(2)` the first pass needed
to make a ramp deterministic is gone.

Verified here: `./gradlew build --offline` and `./gradlew test --offline` green (42/42, jar
produced), `./gradlew simulateJava` runs the loop with no exceptions, and Phoenix 6 26.3.0 /
AdvantageKit 26.0.2 API names were checked against the cached jars with `javap` rather than from
memory. Deliberately **not** done: drive-layer soft limits. `TalonFXConfigurator.apply(
SoftwareLimitSwitchConfigs)` is confirmed present, but which sensor the thresholds follow, whether
they clamp a voltage request at all, and whether they need a Phoenix Pro key could not be settled off
the bench — a second safety layer that silently does nothing is worse than none. `docs/CALIBRATION.md`
spells out the three things to check.

Still needs the robot: the two preset gains and the tolerance are starting points, not tuned values;
buttons 7/8 need their raw IDs confirmed; `EXTENSION_ROTOR_SIGN` still assumes the reading falls while
extending, which the direction fault will now catch rather than the mechanism.

### 中文

第一轮的标定模型在它移植自的那台机构上就是错的。对照 `clone-projects/ArmDemo` 复审后共发现六个问题，
现已全部修复：

1. **丢行程。** ArmDemo 实测这台台架电梯"电机 1 走 3.4 圈、电机 2 走 14.5 圈"，并按各自行程归一化。
   压成一个平均值之后，"任一电机先到即停"会在电机 2 的 14.5 圈里走到 8.95 圈时触发，也就是电梯在
   **62% 行程**处停住、半行程预设落在 **31%**——它朝安全方向失败，所以当时看起来一切正常。
   `ElevatorCalibration` 恢复了"分电机行程"这个坐标，对称机构仍可只填一个共享值；README 里那句
   "举到顶读平均值"——正是产出坏数值的操作步骤——已删除。
2. **限位判断看不到本周期。** 判断写在命令的 `execute()` 里，而 `CommandScheduler` 先跑 `execute()`
   再跑子系统的 `periodic()`，于是每次判断用的都是 20 ms 前的快照，最后那个被批准的电压会在机构已经
   到位之后再多压一个周期。现在所有输出都出自 `periodic()`，命令只申请 `MotionMode`；
   `theSubsystemCutsTheOutputInTheSameCycleItSeesTheLimit` 把这个行为钉住。
3. **CAN 冻结被当成"没到限"。** `refreshAll` 的返回值原先被丢弃。IO 现在会上报驱动器是否应答、上次
   事务是否干净（`isAllGood`）、读数多旧，任一项不满足子系统就写零伏。年龄阈值可在线调且设 0 只关掉
   年龄这一项，因此万一时基在 roboRIO 上表现不同，操作员能在 Dashboard 上单独隔离它。位置同时改用
   速度信号做延迟补偿。
4. **`zeroEncoders()` 没人调用。** 现在是 `rezeroAtLowerLimit()`，只在机构停在下限位时被接受，绑到按键
   7。中途归零会静默挪动所有软件限位，所以它的前提条件改由代码强制。
5. **符号歧义。** 一个带符号的行程常量想同时表达编码器安装方向与接线方向，代码无法区分二者，于是
   "填个负数所有符号自动跟随"并不总成立。现在拆成两个显式常量，行程一律取正值，而机构确实朝指令反
   方向走时会锁存 `Elevator/DirectionReversed` 并停止。
6. **仓库卫生。** 零引用的 `vendordeps/AmLib-2026-Latest.json` 已删除，本地陈旧的 `bin/` 也清了；
   `.github/workflows/test.yml` 让测试终于在 push/PR 上有执行者。

为了让它对别人也值得花时间而新增：`ElevatorIOSim`（同一接口后面的模拟机构，`./gradlew simulateJava`
能在笔记本上跑真实控制回路）、比例式预设（`moveToFractionCommand`、`holdAtFractionCommand`，重力前馈
刻意默认 0V）、`CalibrationSuspect` 诊断（在标定测量那一次日志里就抓住第 1 条的错误），以及 **42 个跑
在手动时钟上的测试**——第一轮为了让斜坡确定化而加的 `Thread.sleep(2)` 已经不需要了。

本机已验证：`./gradlew build --offline`、`./gradlew test --offline` 全绿（42/42，产出 jar），
`./gradlew simulateJava` 循环正常运行无异常，Phoenix 6 26.3.0 与 AdvantageKit 26.0.2 的 API 名字是用
`javap` 对着缓存 jar 核过的，不是凭记忆。刻意**没做**的是驱动器层软限位：`TalonFXConfigurator.apply(
SoftwareLimitSwitchConfigs)` 确认存在，但阈值跟哪个传感器、是否真的约束电压请求、是否需要 Phoenix Pro
